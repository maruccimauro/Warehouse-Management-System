# Diseño de base de datos

Esquema físico de las tablas de E2 a E6 en PostgreSQL: tipos, claves, restricciones, triggers e índices, con la consulta o pantalla que justifica cada índice. Las entidades y sus estados están en [domain-model.md](domain-model.md); las reglas citadas, en [business-rules.md](../02-analysis/business-rules.md).

El DDL de este documento es la referencia que reproducen las migraciones de Laravel. Lo que el Schema Builder no expresa (índices parciales, `NULLS NOT DISTINCT`, claves foráneas compuestas sobre restricciones únicas compuestas, triggers, secuencias) se escribe con `DB::statement` en la migración del módulo dueño de la tabla. El DDL completo se validó ejecutándolo sobre PostgreSQL 17 (E0.08) y se revalidó sobre PostgreSQL 18.7 el 23/11/2026 (E2.01): 35 tablas y 5 triggers sin errores.

## Convenciones

| Aspecto | Criterio | Fundamento |
| - | - | - |
| Versión | PostgreSQL 15 o superior | `UNIQUE NULLS NOT DISTINCT` en `stocks` y `categories` |
| Claves primarias | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Estándar SQL, sin secuencias huérfanas; tamaño suficiente para `stock_movements` |
| Cantidades | `BIGINT` en unidad base | [ADR-005](adr/005-integer-quantities.md) |
| Importes y porcentajes | `NUMERIC(14,2)` y `NUMERIC(5,2)` | Aritmética exacta |
| Fechas y horas | `TIMESTAMPTZ` con precisión de microsegundos, almacenadas en UTC; `DATE` para fechas de calendario | Sin ambigüedad de zona horaria (E1.03). Laravel usa precisión 0 por defecto; `AppServiceProvider` la anula con `Schema::defaultTimePrecision(null)` |
| Estados y listas cerradas | `VARCHAR` con `CHECK (... IN (...))` | Un `ENUM` de PostgreSQL no admite quitar valores; un `CHECK` se reemplaza en una migración |
| Códigos de negocio | `CHECK (code = upper(code))` en SKU, códigos de depósito, zona, ubicación y cliente | La unicidad no depende de mayúsculas al escanear o tipear |
| Claves foráneas | `ON DELETE` restrictivo (predeterminado) en todas | Los datos maestros se desactivan, nunca se borran; los documentos se cancelan |
| Coherencia por depósito | Claves foráneas compuestas `(id, warehouse_id)` | La base impide que un documento, movimiento o existencia mezcle depósitos, sin triggers |
| Referencias polimórficas | `reference_type` y `reference_id` con `CHECK` sobre los tipos admitidos | Mantiene la dirección de dependencias de [ADR-001](adr/001-modular-monolith.md): `Inventory` no conoce las tablas de los módulos que lo usan. Los valores son alias del morph map de Laravel (`Relation::enforceMorphMap`), no nombres de clase |
| Documentos | Número legible `PREFIJO-AAAA-NNNNNN` desde una secuencia por tipo de documento, con `CHECK` de formato | La secuencia no requiere bloqueo; los huecos por transacciones revertidas son aceptables porque el número no es fiscal |
| Reversión de documentos | Reversión parcial por posición y cantidad (DM-15): cada reversión es una operación `reversal` propia, con usuario, fecha y motivo, cuyas líneas apuntan a la línea original (`reverses_movement_id`). El documento acumula lo revertido por posición (`quantity_reversed`) y no cambia de estado: muestra por posición el original, lo revertido y el neto, como un documento de material de SAP frente a sus anulaciones | Mismo patrón en recepciones, tareas de guardado, líneas de picking, despachos e inventarios físicos. El límite de lo revertido lo garantiza un trigger sobre `stock_movements` ([ADR-013](adr/013-partial-reversal-by-line.md)) |
| Nombres de restricciones | `{tabla}_{columnas}_{tipo}`, igual que Laravel | Las violaciones se traducen a errores de dominio por nombre de restricción |

| Prefijo | Documento | Secuencia |
| - | - | - |
| `OP` | Operación de inventario | `inventory_operation_number_seq` |
| `PO` | Orden de compra | `purchase_order_number_seq` |
| `GR` | Recepción | `goods_receipt_number_seq` |
| `SO` | Pedido | `customer_order_number_seq` |
| `DS` | Despacho | `dispatch_number_seq` |
| `ST` | Inventario físico | `stocktake_number_seq` |

## Concurrencia

| Aspecto | Criterio |
| - | - |
| Aislamiento | `READ COMMITTED` (predeterminado) con bloqueos explícitos; la disponibilidad se valida después de bloquear ([ADR-003](adr/003-pessimistic-concurrency-control.md)) |
| Reintentos | `DB::transaction($callback, 3)` ante deadlock y falla de serialización ([ADR-004](adr/004-concurrency-retries.md)) |
| Orden global de bloqueo | 0) fila del depósito (`FOR SHARE` para operar, `FOR NO KEY UPDATE` para desactivarlo, REG-015); 1) cabecera del documento raíz (`FOR UPDATE`); 2) documentos dependientes y líneas, por `id` ascendente; 3) ubicaciones (`FOR SHARE` para mover, `FOR UPDATE` para cambiar su estado), por `id`; 4) filas de `stocks` (`FOR UPDATE`), por `id` en una sola consulta |
| Cola de picking | `GET /picking-tasks/next` toma la tarea con `FOR UPDATE SKIP LOCKED` para que dos operadores no compitan por la misma |
| Estado del producto | Las operaciones de E3 a E6 leen el producto con `FOR SHARE` para validar su estado (REG-017); `UpdateProduct` lo cambia con `FOR NO KEY UPDATE`, igual que el nivel 0 del depósito. No necesita nivel en el orden global: `FOR SHARE` no se excluye consigo mismo, y `UpdateProduct` no tiene otro bloqueo tomado, así que no puede cerrar un ciclo de espera. `FOR NO KEY UPDATE` tampoco frena el `FOR KEY SHARE` de las claves foráneas hacia `products` |
| Árbol de categorías | Todo cambio de estructura (alta con padre, cambio de padre) toma `pg_advisory_xact_lock(205001)` antes de recorrer el árbol (REG-016). Sin él, mover A bajo B y B bajo A en paralelo crearía un ciclo que ninguna de las dos transacciones ve. No participa del orden global: ninguna operación de inventario lo toma |

El orden 3 antes de 4 es el de [ADR-003](adr/003-pessimistic-concurrency-control.md), corregido en E0.08. Con el orden inverso, la aprobación de un inventario físico (que bloquea ubicaciones y luego existencias) y un movimiento concurrente sobre esas ubicaciones (que bloquea existencias y luego ubicaciones) forman un ciclo que PostgreSQL resuelve abortando una de las dos transacciones. Con un único orden jerárquico, ubicación antes que existencia, el ciclo no puede formarse.

Más las tablas de `spatie/laravel-permission` (`roles`, `permissions`, `model_has_roles`, `model_has_permissions`, `role_has_permissions`), con la estructura de su migración publicada sin equipos y los tipos adaptados a las convenciones (`IDENTITY`, `TIMESTAMPTZ`); sus pivotes conservan `ON DELETE CASCADE` porque son configuración de acceso, no historia, y `model_type` guarda el alias del morph map (`user`). Las tablas de infraestructura de Laravel (`sessions`, `cache`, `jobs`, `password_reset_tokens`) quedan sin cambios respecto de sus migraciones publicadas.

Notas:

- `users.locale` es el idioma preferido que resuelve el middleware de idioma. La base exige solo el formato; la lista de idiomas admitidos es configuración (`app.supported_locales`) y se valida en la aplicación, para que agregar un idioma no requiera migración.
- Una restricción `CHECK` se cumple cuando la expresión es nula; por eso `max_units > 0` y las dimensiones del producto admiten `NULL` sin cláusula adicional.
- `locations.is_system` es una columna generada a partir de `system_role` y no puede contradecirlo. El glosario conserva `Location.is_system`.
- Al crear un depósito, la Action `CreateWarehouse` agrega en la misma transacción una zona de sistema por rol (`is_system`, tipos `receiving`, `packing` y `dispatch`) con una ubicación cada una; zona y ubicación comparten el código: `RECEPCION`, `PACKING` y `DESPACHO`.
- La ubicación de sistema `dispatch` se crea con el depósito (E2.02) pero no recibe movimientos en el MVP: el despacho descuenta desde `packing`. Queda disponible para una etapa de preparación de carga.
- `UNIQUE NULLS NOT DISTINCT (parent_id, name)` impide dos categorías raíz con el mismo nombre; un `UNIQUE` común lo permitiría. Los ciclos de más de un nivel y la profundidad máxima de 5 niveles los valida la Action con el árbol bloqueado (REG-016).
- `products.barcode` admite `NULL` en varias filas: la API guarda un código vacío como nulo. No se normaliza a mayúsculas porque Code 128 las distingue; un código numérico con largo de GTIN exige dígito verificador válido.
- `product_warehouse_settings` guarda lo que un producto tiene de propio en cada depósito, como los datos de centro (`MARC`) de SAP (DM-21). Sin fila, el producto usa los valores por defecto en ese depósito: `min_stock` 0, sin alerta de stock crítico. Reemplaza a la columna `products.min_stock` del diseño de E0.

```sql
CREATE FUNCTION validate_movement_reversal() RETURNS trigger
LANGUAGE plpgsql AS $$
DECLARE
  operation_type VARCHAR(30);
  reversed_operation_id BIGINT;
  original stock_movements%ROWTYPE;
  expected_code SMALLINT;
  already_reversed BIGINT;
BEGIN
  SELECT type, reverses_operation_id INTO operation_type, reversed_operation_id
    FROM inventory_operations WHERE id = NEW.operation_id;

  IF NEW.reverses_movement_id IS NULL THEN
    IF operation_type = 'reversal' THEN
      RAISE EXCEPTION 'REVERSAL_LINE_WITHOUT_ORIGINAL' USING ERRCODE = 'check_violation';
    END IF;
    RETURN NEW;
  END IF;

  -- Serializa las reversiones concurrentes de una misma línea.
  SELECT * INTO original FROM stock_movements WHERE id = NEW.reverses_movement_id FOR UPDATE;

  SELECT reversal_code INTO expected_code
    FROM movement_types WHERE code = original.movement_code AND direction = original.direction;

  IF operation_type IS DISTINCT FROM 'reversal'
     OR reversed_operation_id IS DISTINCT FROM original.operation_id
     OR original.reverses_movement_id IS NOT NULL
     OR NEW.stock_id <> original.stock_id
     OR sign(NEW.delta) = sign(original.delta)
     OR NEW.movement_code <> expected_code THEN
    RAISE EXCEPTION 'REVERSAL_LINE_MISMATCH' USING ERRCODE = 'check_violation';
  END IF;

  SELECT COALESCE(sum(abs(delta)), 0) INTO already_reversed
    FROM stock_movements WHERE reverses_movement_id = original.id;

  IF already_reversed + abs(NEW.delta) > abs(original.delta) THEN
    RAISE EXCEPTION 'REVERSAL_EXCEEDS_REMAINING' USING ERRCODE = 'check_violation';
  END IF;

  RETURN NEW;
END;
$$;

CREATE TRIGGER stock_movements_validate_reversal BEFORE INSERT ON stock_movements
  FOR EACH ROW EXECUTE FUNCTION validate_movement_reversal();
CREATE TRIGGER audit_logs_prevent_mutation BEFORE UPDATE OR DELETE ON audit_logs
  FOR EACH ROW EXECUTE FUNCTION prevent_ledger_mutation();
```

Notas:

- **Unicidad de la referencia de una operación (INV-007).** `inventory_operations_reference_unique` impide que un mismo documento origine dos operaciones: una recepción, una tarea de putaway, una línea de picking, un despacho o un inventario físico tienen como máximo una. Es la garantía en base de datos contra la doble confirmación. El `operation_id UNIQUE` de los documentos solo impide que dos documentos apunten a la misma operación, no que un documento genere dos; se conserva como navegación directa. Las operaciones sin documento (`transfer`, ajustes, `reversal`) tienen referencia nula y no se ven afectadas, porque un `UNIQUE` común admite varias filas con nulos.
- **Tipo y referencia.** `inventory_operations_type_reference_check` fija qué documento corresponde a cada tipo y exige referencia nula en los tipos sin documento. Usa `IS NOT DISTINCT FROM` porque un `CHECK` que evalúa a `NULL` se considera cumplido: una versión con `OR` y comparaciones simples aceptaba una operación `receipt` sin documento (detectado al validar este DDL).
- **Coherencia de depósito en el libro.** La clave foránea compuesta de `stock_movements` hacia `inventory_operations (id, warehouse_id)` y hacia `stocks (id, warehouse_id, product_id, location_id)` garantiza que todos los movimientos de una operación pertenezcan a su depósito y que las columnas desnormalizadas `product_id` y `location_id` coincidan con la existencia. El costo es un índice único adicional sobre `stocks`.
- **Un movimiento por existencia y operación.** `stock_movements_operation_id_stock_id_unique` impide dos líneas sobre la misma fila en una operación; una transferencia con origen igual a destino falla también en la base (INV-004).
- **Reversión parcial (DM-15).** Una operación admite varias reversiones, cada una sobre las líneas y cantidades elegidas; por eso `reverses_operation_id` ya no es único. Cada línea de reversión apunta con `reverses_movement_id` a la línea original, y `stock_movements_validate_reversal` garantiza en la base que esté sobre la misma existencia, con el signo opuesto y el código de reversión de la original, que la original no sea a su vez una reversión y que lo revertido acumulado no supere su cantidad (`REVERSAL_EXCEEDS_REMAINING`). El trigger bloquea la línea original con `FOR UPDATE`, de modo que dos reversiones concurrentes de la misma línea se serializan y la segunda ve lo que revirtió la primera; un bloqueo de fila no dispara el trigger de inmutabilidad. Revertir un documento completo es revertir todas sus líneas por su saldo. Las líneas de una misma posición se revierten juntas (en una transferencia, la salida del origen y la entrada del destino por la misma cantidad); eso lo valida `ReverseOperation`. El motivo de la reversión es obligatorio en `notes`.
- **`stock_movements.reservation_id`** registra la reserva que consume la línea (pick y despacho), lo que hace explícita la distinción de INV-005 entre retiros libres y retiros contra reserva.
- **`ON CONFLICT`.** La creación concurrente de existencias (paso 2 de `StockLedger`) usa `ON CONFLICT ON CONSTRAINT stocks_product_id_location_id_lot_id_unique DO NOTHING`, que nombra la restricción en lugar de inferirla de columnas nulas.
- **Motivo `initial_load`.** Se agrega a la lista cerrada de INV-008 para la carga inicial de E3.06, que se registra como `adjustment_in` con código 561. El tipo `return` del plan de E3 se incorpora junto con el flujo de devoluciones de clientes.
- **Códigos de movimiento (DM-09).** Cada movimiento lleva su código, como la posición de un documento de material de SAP; la operación conserva su `type` para la lógica de la aplicación. La columna generada `direction` y la clave foránea compuesta hacia `movement_types` impiden en la base un código con el signo equivocado, por ejemplo un 101 con delta negativo. La reversión usa en cada línea el `reversal_code` del movimiento original. La correspondencia por tipo de operación la valida `StockLedger`:

  | Tipo de operación | Códigos | Equivalente SAP |
  | - | - | - |
  | `receipt` | 101 | Entrada por pedido (MIGO) |
  | `putaway` | 911 | Tarea de almacén WM/EWM, sin clase de movimiento IM |
  | `transfer` | 931 | Traspaso entre ubicaciones WM/EWM |
  | `adjustment_in` | 561 (`initial_load`), 712 (`found`, `correction`) | Carga inicial 561, diferencias de almacén 712 |
  | `adjustment_out` | 551 (`damage`), 711 (`loss`, `correction`) | Desguace 551, diferencias de almacén 711 |
  | `pick` | 921 | Tarea de picking WM/EWM |
  | `dispatch` | 601 | Salida de mercancías de la entrega |
  | `stocktake_adjustment` | 701, 702 | Diferencias de inventario (MI07) |
  | `reversal` | Código de reversión de cada línea original | 102, 562, 552, 602; anulación con MBST o VL09 |

  En SAP la reversión suele ser el código siguiente (101 y 102); las parejas 701/702 y 711/712 son las dos direcciones de un mismo concepto y se usan una como reversión de la otra. Una reversión se distingue de un movimiento original con el mismo código por el `reverses_operation_id` de su operación.
- **Trigger de inmutabilidad (INV-003, INV-012).** Es de nivel de fila, por lo que no actúa sobre `TRUNCATE`; la limpieza por truncado de las pruebas de concurrencia de E3.14 sigue funcionando. En producción, la defensa contra `TRUNCATE`, `ALTER TABLE ... DISABLE TRIGGER` y `session_replication_role` es de privilegios: las migraciones corren con el rol dueño del esquema y la aplicación con un rol sin propiedad de las tablas ni privilegio `TRUNCATE` (se implementa en E8).
- **Idempotencia.** La clave se inserta en la misma transacción que la operación ([ADR-007](adr/007-idempotency.md)). Una petición concurrente con la misma clave espera en el índice único hasta que la primera termina: si la primera confirmó, la segunda recibe la violación de unicidad y devuelve la respuesta almacenada; si la primera falló, la segunda continúa. El 409 `IDEMPOTENCY_REQUEST_IN_PROGRESS` corresponde a esa espera cuando supera `lock_timeout`. Una petición rechazada por una regla de negocio no deja clave y su reintento se evalúa de nuevo.
- **Conciliación ampliada.** `wms:reconcile` verifica, además de lo indicado en E3.13, que `quantity_blocked` sea igual a la suma de los bloqueos activos de la fila.

Notas:

- **Segregación en la base (REG-001).** `purchase_orders_self_approval_check` impide que el aprobador sea el creador aunque la Policy fallara.
- **Semántica de cantidades en la recepción.** `goods_receipt_items.quantity_received` es lo aceptado, que ingresa al stock; `quantity_rejected` no ingresa (REG-004). Lo llegado físicamente es la suma de ambas. INV-006 compara el acumulado de `purchase_order_items.quantity_received` con `quantity_ordered * (1 + over_receipt_tolerance_pct / 100)`; no hay `CHECK` porque el permiso `receiving.over_receive` habilita superarlo.
- **Reversión parcial de la recepción.** `goods_receipt_items.quantity_reversed` acumula lo revertido con 102 por posición y la Action resta lo mismo de `purchase_order_items.quantity_received`. Solo se revierte lo que está libre en RECEPCION: lo comprometido por una solicitud de guardado pendiente exige revertir antes esa solicitud (orden inverso de la cadena, aplicado por cantidad). La recepción no cambia de estado: muestra por posición lo aceptado, lo revertido y el neto.
- **Coherencia de líneas.** La clave foránea compuesta `(purchase_order_item_id, product_id)` impide que una línea de recepción apunte a una línea de orden de otro producto. Con `MATCH SIMPLE` (predeterminado), una recepción ciega con `purchase_order_item_id` nulo no se verifica contra la orden. Que la línea pertenezca a la misma orden de la recepción lo valida la Action.
- **Solicitud de guardado (DM-16).** Al emitirse crea una reserva (`reference_type = 'putaway_task'`) sobre la existencia de origen por su cantidad, de modo que esa mercadería no se ajusta ni se transfiere mientras la solicitud la espera (INV-005). Se revierte en parte o en total, con motivo, por quien la ejecuta o por un supervisor; cada reversión queda en `putaway_task_reversals` con su usuario y su hora. Antes de guardar, la reversión no mueve stock (la mercadería nunca salió del origen): suma a `quantity_returned` y reemplaza la reserva por una nueva por el saldo; si se revierte todo, la solicitud pasa a `completed` con guardado 0 y sin operación, como una orden de transporte confirmada con diferencia. Después de guardar, la reversión es una operación 912 desde los destinos al origen, referenciada en `operation_id`, y suma a `quantity_reversed`; la solicitud sigue `completed` y muestra lo guardado, lo revertido y el neto. Completar la solicitud guarda `quantity - quantity_returned` y consume la reserva. `putaway_task_reversals` es de solo inserción, como el libro.
- **Recepción totalmente rechazada.** Se confirma sin operación de inventario (`operation_id` nulo); la doble confirmación la impide el bloqueo de cabecera y la validación de estado.

- **Cantidades de la línea de pedido.** Cada unidad pedida está en uno de cuatro estados: sin asignar, reservada en almacenamiento pendiente de pickear (`quantity_reserved`), pickeada y en PACKING (`quantity_picked`) o faltante (`quantity_short`). `customer_order_items_allocation_check` impide que la suma supere lo pedido. Lo despachado es lo pickeado de un pedido en `dispatched`, registrado en su despacho vigente.
- **Conciliación de pedidos.** `wms:reconcile` se extiende en E5 para verificar, por línea de pedido no despachada, que `quantity_reserved` sea igual a la suma de reservas activas fuera de PACKING y `quantity_picked` a la suma de reservas activas en PACKING.
- **REG-007 en la base.** `picking_tasks_one_in_progress_per_operator_unique` impide dos tareas `in_progress` del mismo operador aunque dos peticiones de inicio lleguen en paralelo; la violación se traduce a 409 `PICKING_TASK_IN_PROGRESS`.
- **Prioridad desnormalizada.** `picking_tasks.priority` se copia del pedido al generar la tarea para que la cola de E5.05 se resuelva con un índice parcial sin unir con `customer_orders`.
- **Despachos (DM-10).** Cada salida es un documento propio, como la salida de mercancías de una entrega en SAP. Un despacho se revierte en parte o en total con 602 por producto y cantidad (DM-15, DM-17): lo revertido vuelve a PACKING como stock libre y se crea una solicitud de guardado de retorno (`origin_type = 'dispatch'`). Ni el despacho ni el pedido cambian de estado: lo despachado neto por producto es la suma de los 601 del despacho menos sus 602 (despachado 10, revertido 10, neto 0). Un pedido tiene a lo sumo un despacho, y su operación es única por la referencia de INV-007. `dispatches_one_confirmed_per_order_unique` impide dos despachos vigentes del mismo pedido aunque dos peticiones lleguen en paralelo. `operation_id` se completa en la misma transacción que crea el despacho, igual que en las recepciones.
- **Reversión de picking.** Una línea se revierte en parte o en total con 922; `quantity_reversed` acumula lo revertido; la línea no cambia de estado. La cantidad revertida vuelve a reservarse en la ubicación de origen, la reserva de PACKING se reemplaza por una por el saldo y se crea una línea pendiente por lo revertido, que referencia la reserva nueva, en una tarea nueva del pedido o en su tarea abierta. La tarea original no cambia de estado. `picking_task_lines_reservation_id_unique` se mantiene porque cada línea tiene su propia reserva.
- **Baja por daño en PACKING (DM-13).** Es una operación `adjustment_out` con motivo `damage` y referencia nula, como cualquier ajuste; su movimiento 551 lleva en `reservation_id` la reserva de PACKING que consume, y esa reserva referencia la línea de pedido. Si la baja es menor que la reserva, la reserva queda `consumed` por lo dado de baja y se crea una reserva activa nueva por el resto, de modo que la conciliación de `quantity_picked` contra las reservas activas en PACKING se mantiene. No requiere cambios en el DDL.
- **Bultos.** Se agregan y modifican con el pedido en `picked`; al pasar a `packed` quedan fijos. Que un bulto y sus líneas pertenezcan al mismo pedido lo valida la Action.

- **Segregación en la base (REG-011).** `stocktake_items_recount_other_operator_check` impide que el mismo operador cuente y recuente una línea. La regla del aprobador (INV-010, DM-08) compara contra todas las líneas del inventario y la valida la Action.
- **Umbral de reconteo.** La diferencia porcentual es `|final - system| / system * 100`. Con `system_quantity = 0` y conteo distinto de cero (producto no registrado), el reconteo es siempre obligatorio.
