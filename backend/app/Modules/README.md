# Módulos

Monolito modular (ADR-001): un módulo por contexto de dominio, con una base PostgreSQL compartida.

| Módulo | Responsabilidad |
| - | - |
| `Identity` | Usuarios, autenticación, roles y permisos, asignación de depósitos |
| `Warehouse` | Depósitos, zonas y ubicaciones |
| `Catalog` | Productos, categorías, unidades de medida y proveedores |
| `Inventory` | Existencias y libro de movimientos |
| `Procurement` | Órdenes de compra |
| `Receiving` | Recepciones y tareas de ubicación (putaway) |
| `Fulfillment` | Pedidos, reservas, picking, packing y despacho |
| `Stocktaking` | Inventario físico, conteos y ajustes |
| `Reporting` | Reportes y consultas de solo lectura |
| `Audit` | Registro de auditoría |

## Estructura de un módulo

Cada directorio se crea cuando el módulo lo necesita.

```
app/Modules/{Nombre}/
├── {Nombre}ServiceProvider.php   extiende App\Shared\Providers\ModuleServiceProvider
├── Actions/                      casos de uso: una clase por operación de negocio
├── Contracts/                    interfaces que otros módulos usan por inyección (AuditLogger)
├── Data/                         objetos de valor que reciben las Actions (plantillas, criterios)
├── Database/Factories/           factories de los modelos del módulo
├── Database/Migrations/          migraciones del módulo, cargadas por el provider
├── Database/Seeders/             datos de desarrollo idempotentes, llamados desde DatabaseSeeder
├── Exceptions/                   excepciones de dominio con código estable (ADR-010)
├── Http/Controllers/
├── Http/Requests/                autorizan con la Policy antes de validar (404 antes que 422)
├── Http/Resources/               forma pública de cada modelo en la API
├── Models/
├── OpenApi/                      extensiones de Scramble propias del módulo (ADR-012), registradas
│                                 en App\Providers\ApiDocumentationServiceProvider
├── Policies/                     declaradas en $policies del provider
├── Rules/                        reglas de validación propias del dominio (código de barras)
├── Services/                     implementaciones de los contratos, enlazadas en el provider, y
│                                 servicios de dominio que comparten varias Actions (CategoryHierarchy)
└── Routes/api.php                registrado bajo /api/v1 con el grupo de middleware api
```

## Migraciones

Reproducen el DDL de `docs/03-architecture/database-design.md`.

| Aspecto | Cómo se escribe | Motivo |
| - | - | - |
| Clave primaria | `$table->id()->generatedAs()` | `id()` solo genera `bigserial`; con `generatedAs()` es `GENERATED BY DEFAULT AS IDENTITY` |
| Fechas y horas | `timestampTz()`; `created_at` y `updated_at` con `useCurrent()` cuando el DDL los declara `NOT NULL DEFAULT now()` | `timestamp()` y `timestamps()` generan `timestamp without time zone`. La precisión de microsegundos la fija `AppServiceProvider` |
| Cantidades | `bigInteger()` en unidad base (ADR-005) | Aritmética entera exacta |
| Lo que el Schema Builder no expresa | `DB::statement` en la misma migración: `CHECK`, índices parciales, `NULLS NOT DISTINCT`, claves foráneas compuestas, columnas generadas, triggers | El DDL es la referencia |
| Nombres de restricciones | `{tabla}_{columnas}_{tipo}` | `DatabaseErrorTranslator` traduce por nombre |

`tests/Feature/Database/SchemaConventionsTest.php` recorre el esquema migrado y falla ante una columna `timestamp without time zone`, una precisión distinta de microsegundos o una secuencia `serial`. Las tablas de infraestructura de Laravel (`sessions`, `cache`, `jobs` y afines) quedan como sus migraciones publicadas y se excluyen.

## Convenciones de API

| Aspecto | Convención | Motivo |
| - | - | - |
| Respuesta | API Resource por modelo en `Http/Resources/`; nunca el modelo serializado directo | El contrato no cambia al agregar columnas, y Scramble lo documenta a partir del Resource (ADR-012) |
| Listado de datos maestros | El Form Request extiende `App\Shared\Http\Listing\ListRequest` y el controlador devuelve `XResource::collection($request->paginate($query))` | Paginación por página con total: la grilla muestra el total y salta de página. El libro de movimientos de E3 usa cursor |
| Forma del listado | `data`, `links` (`first`, `last`, `prev`, `next`) y `meta` (`current_page`, `last_page`, `per_page`, `total`, `from`, `to`, `path`) del paginador de Laravel | Formato estándar del framework |
| Página | `page` desde 1; `per_page` de 50 por defecto y 200 como máximo | Acota el costo de una petición |
| Filtros | `filter[campo]=valor`; cada listado declara sus campos en `filters()` con `FilterMode::Exact`, `Partial` (fragmento sin distinguir mayúsculas, comodines escapados) o `In` (`filter[campo][]=a&filter[campo][]=b`). Un criterio que no es una columna del modelo (una relación, como `filter[role]` en usuarios) se declara `Custom` y lo aplica el listado en `applyCustomFilter()`. Los valores que no son texto llevan su regla en `filterValueRules()` | Lista blanca: la columna sale de la declaración, nunca de la petición. Un criterio vacío no restringe, como en una pantalla de selección |
| Orden | `sort=campo` o `sort=-campo`, entre los campos de `sorts()`; sin `sort`, `defaultSort()`. La clave primaria desempata | Sin desempate, dos páginas pueden repetir o saltear filas con el mismo valor |
| Parámetro no declarado | 422 `VALIDATION_FAILED` con el campo en `errors` | Un filtro ignorado en silencio devuelve datos que el usuario cree filtrados |
| Modelos de la ruta | Vinculación explícita con `Route::model()` en el provider del módulo; los identificadores con patrón `[1-9][0-9]{0,17}` | El Form Request usa el modelo antes del controlador, y la vinculación implícita solo resuelve lo que declara la firma del controlador. Un identificador no numérico o fuera de `BIGINT` responde 404 y no un error de conversión de PostgreSQL |
| Valor único repetido | El Form Request lo valida con `unique`; la restricción de la base es el respaldo ante una carrera y se declara en `$uniqueConstraintFields` del provider (restricción => campo del formulario), que responde 422 `VALUE_ALREADY_EXISTS` con `context.field` | Dos peticiones simultáneas pueden pasar la validación; la base rechaza la segunda y el cliente marca el mismo campo que con la validación |

`tests/Feature/Http/ListingConventionsTest.php` prueba el contrato de listados y `tests/Feature/Database/UniqueConstraintTranslationTest.php` provoca cada restricción única registrada contra el esquema real.

## Documentación OpenAPI

La especificación se genera desde el código con Scramble (ADR-012) y se versiona en `docs/03-architecture/openapi.json`. Al agregar o cambiar un endpoint:

| Caso | Qué hacer |
| - | - |
| Cualquier cambio de contrato | `composer openapi` y commitear `openapi.json` con el cambio: el CI falla si la especificación versionada difiere de la generada |
| Excepción de dominio lanzada en el controlador, una Action, un servicio o un closure que reciben | Nada: `CalledMethodExceptions` la propaga hasta la operación |
| Error que el análisis no ve (un error de la base traducido por `DatabaseErrorTranslator`, una llamada sobre un valor sin tipo) | `@throws` en el método que lo origina. Toda Action que escribe una columna con restricción en `$uniqueConstraintFields` declara `@throws ValueAlreadyExists` |
| Campo que no se acepta | Regla `prohibited` sola: `ProhibitedFieldRule` lo quita del cuerpo documentado |
| Operación que modifica stock (E3 en adelante) | Middleware con el alias `Idempotency::MIDDLEWARE`: la cabecera `Idempotency-Key` y sus errores se documentan solos |
| Error en un middleware propio | Extensión de operación en `OpenApi/` del módulo (ver `Identity\OpenApi\SpaSessionOperation`), antepuesta en el provider de la documentación |

Todo código documentado tiene que estar en el catálogo de `business-rules.md` con el mismo estado; lo verifica `tests/Feature/OpenApi/OpenApiSpecificationTest.php`.

## Alcance por depósito

Todo recurso que pertenece a un depósito respeta REG-005 con `App\Modules\Identity\Authorization\WarehouseAccess` (ADR-009):

- El modelo usa el trait `App\Modules\Warehouse\Models\Concerns\ScopedByWarehouse`, que da los scopes `visibleTo($user)` para listados y `operableBy($user)` para elegir dónde operar. Si la columna no es `warehouse_id`, el modelo redefine `warehouseScopeColumn()`.
- La Policy devuelve `authorizeView()` para consultar y `authorizeOperation()` con el permiso de la acción para operar. El orden es 404 fuera del alcance de consulta, 403 sin operación en el depósito y 403 sin el permiso.
- Toda Action que opera sobre un depósito (movimientos, documentos, bloqueo de ubicaciones) llama primero, dentro de su transacción, a `App\Modules\Warehouse\Actions\LockActiveWarehouse`: toma la fila del depósito con `FOR SHARE` (nivel 0 de ADR-003) y responde 422 `WAREHOUSE_INACTIVE` si está inactivo (REG-015). El mantenimiento de zonas y ubicaciones no es una operación y no la llama.

## Estado de la cuenta e idioma

`IdentityServiceProvider` agrega al grupo `api` tres middlewares que valen para toda ruta autenticada de cualquier módulo, sin declararlos en cada archivo de rutas:

- `ApplyPreferredLocale`: el idioma del usuario (`users.locale`) tiene prioridad sobre el que resolvió `SetLocale` con `Accept-Language` (E2.21). `SetLocale` es global y corre antes de que exista la sesión, por eso la preferencia se aplica acá, antes de validar la petición.
- `EnsureUserIsActive`: la sesión de un usuario desactivado se cierra con 401 (REG-020).
- `RequirePasswordChange`: con una contraseña inicial o reseteada, solo `auth.me`, `auth.logout` y `me.password.update` responden; el resto, 403 `PASSWORD_CHANGE_REQUIRED` (REG-021). Una ruta nueva que deba admitirse en ese estado se agrega a `RequirePasswordChange::ALLOWED_ROUTES`.

El modelo `User` repite en `$attributes` los valores por defecto de la base (`is_active`, `password_change_required`, `locale`, `show_technical_names`): sin ellos, un usuario recién creado no los tiene en memoria y el middleware lo tomaría como inactivo.

## Auditoría

Las operaciones críticas (INV-012) se auditan con el contrato `App\Modules\Audit\Contracts\AuditLogger` (ADR-008):

- La Action lo recibe por inyección y llama a `record()` dentro de su `DB::transaction`, después de aplicar el cambio, con la acción en la forma `entidad.verbo` (`location.blocked`) y los valores afectados antes y después como valores planos.
- El modelo auditado necesita un alias en el morph map, que el provider de su módulo registra con `Relation::morphMap()`: Identity activa `enforceMorphMap`.
- Acciones registradas: `location.blocked`, `location.unblocked`, `warehouse.activated` y `warehouse.deactivated`; sin depósito, porque son globales, `product.status_changed`, `supplier.activated`, `supplier.deactivated`, `user.created`, `user.activated`, `user.deactivated`, `user.roles_changed`, `user.warehouses_changed`, `user.password_reset` y `user.password_changed` (estas dos sin valores: la contraseña nunca se audita).
- Hasta E3 el binding es `NullAuditLogger`; E3 crea `audit_logs` con su trigger de inmutabilidad y reemplaza el binding sin tocar las Actions. Las pruebas reemplazan el contrato por `Tests\Support\RecordingAuditLogger`, un registro en memoria que verifica que se audita dentro de la transacción.

## Reglas

- Solo `Inventory` escribe en `stocks` y `stock_movements`. Los demás módulos invocan sus Actions.
- Un módulo usa otro a través de sus Actions y modelos, nunca de sus controladores.
- Lo transversal que no es de dominio (manejo de errores, controlador de health, provider base) va en `app/Shared`.
- Un módulo nuevo se registra en `bootstrap/providers.php`. `tests/Feature/ModuleRegistrationTest.php` verifica que la lista coincida con ADR-001.
- `tests/Architecture/ModuleBoundariesTest.php` hace cumplir estas reglas con las pruebas de arquitectura de Pest: `Shared` no depende de los módulos, ningún módulo usa la capa HTTP de otro y los modelos de `Inventory` solo se usan en `Inventory` y en `Reporting`.
